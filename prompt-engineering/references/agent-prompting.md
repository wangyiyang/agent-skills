# Agent Prompting

## 目标

面向 agent 的 prompt 不是“让模型回答问题”，而是“让模型在约束下稳定行动”。因此重点不只是内容质量，还包括执行顺序、停止条件、工具使用边界和产出结构。

## 设计顺序

1. 角色：它是谁，擅长什么。
2. 主目标：这一轮必须完成什么。
3. 工作流：先做什么，后做什么。
4. 工具边界：什么场景必须用工具，什么场景不能用。
5. 输出契约：最终交付物长什么样。
6. 风险边界：何时停下来问，何时可以默认假设。

## 常用骨架

```markdown
You are a {role}.

Primary goal:
- {goal}

Required workflow:
1. {step_1}
2. {step_2}
3. {step_3}

Tool rules:
- Must use {tool} when {condition}
- Do not use {tool} when {condition}

Output:
- Return {artifact}
- Include {validation}

Stop and ask if:
- {risk_condition}
```

## 关键原则

### 上下文窗口是公共资源

- 不重复模型已经知道的常识
- 不把大段参考资料直接塞进主 prompt
- 只保留能改变执行行为的说明

### 指令优先级必须清楚

推荐顺序：

1. 不可违反的硬规则
2. 主要目标
3. 工作流
4. 风格偏好

如果顺序混乱，模型更容易在“风格”上过拟合，在“目标”上失焦。

### 自由度匹配任务风险

- 代码审查、方案讨论：高自由度
- 模板化编辑、报告生成：中自由度
- 安全检查、迁移执行：低自由度

### 先定义停止条件

如果 agent 不知道何时该停，它就容易越界。

必须明确：

- 何时只分析，不执行
- 何时执行到某一步就结束
- 何时遇到风险必须提问

## 编写 skills / commands / hooks 时的建议

- 触发描述写“什么时候用”，不要只写“它是什么”
- 主文件只保留工作流和决策规则
- 大量例子、技术背景、变体细节放到 `references/`
- 若一个 skill 超过 500 行，主动拆分

## 常见错误

- 约束很多，但没有优先级
- 工具规则模糊，导致该查不查、该停不停
- 输出要求太抽象，例如“写得专业一点”
- 同时要求“高度自主”又“每一步都先问”
